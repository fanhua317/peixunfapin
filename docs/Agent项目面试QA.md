# Agent 项目面试 QA

更新时间：2026-06-26

本文按真实项目实现整理，用于面试时解释钜洲培训 Agent 的技术选型、架构取舍、RAG、Agent 路由、记忆、部署和安全治理。

## 1. 项目定位

### Q1：这个项目到底是 Agent 项目还是 RAG 项目？

A：更准确地说，它是一个带 RAG 能力的业务 Agent 项目。RAG 负责从企业资料里找证据，Agent 负责理解用户意图、选择 skill、执行培训发布/查询/删除/软文等动作，并通过确认门禁避免误操作。

### Q2：项目核心闭环是什么？

A：老板端用自然语言创建培训草稿，确认后发布给员工；员工打开专属链接学习讲义、提问、生成考试并提交；系统汇总完成率、成绩和薄弱来源。软文生成、记忆、任务中心和 Trace 是围绕这个闭环扩展出来的能力。

### Q3：它和普通 ChatGPT 套壳有什么区别？

A：普通套壳主要是聊天。本项目有资料导入、知识库版本、混合检索、培训任务、邀请链接、考试、报表、记忆、异步任务和轨迹评测。模型只是其中一个生成组件，不负责直接决定所有业务动作。

### Q4：为什么不直接叫 LMS 或 OA？

A：传统 LMS/OA 更偏固定表单和流程。本项目的入口是自然语言 Agent，用户可以说“给王小明发布电机基础培训，明天下午 6 点前完成”，系统会转成结构化草稿，再由确认流程执行。

## 2. 技术选型

### Q5：为什么后端使用 Node 原生 HTTP？

A：项目早期目标是可控、轻量、便于本地和 Windows Server 部署。Node 原生 HTTP 足够支撑当前 API、静态文件、WebSocket 流式和任务查询；不引入 Express/Fastify 能减少依赖和迁移成本。

### Q6：为什么前端不用 React/Vue？

A：当前界面是老板端聊天、员工端学习、导入管理、任务中心和 Trace 页面，复杂度还可由无构建 ES modules 承担。这样部署包更简单，服务器也不需要前端构建链。

### Q7：为什么默认用 DeepSeek API？

A：长文本讲义、出题和软文对生成质量要求较高。本地 2 核 4GB 服务器更适合跑轻量 query embedding，不适合长期运行聊天大模型。DeepSeek 通过 OpenAI-compatible API 接入，配置简单，成本和质量比较适合当前阶段。

### Q8：为什么没有 API 就不生成？

A：培训讲义和考试题不能靠模板假装生成。项目明确要求：没有可用大模型 API 时，不生成讲义、不出题、不写软文，而是返回清晰错误。

### Q9：OpenClaw Gateway 还有什么用？

A：它是可选兼容入口。项目可以通过 OpenClaw 插件暴露 8 个 training tool 给外部 Agent 调用，但网页端和核心培训流程默认独立运行。保留 Gateway 是为了兼容历史工具入口和未来外部编排，不是默认依赖。

### Q10：为什么把数据放到 `D:\juzhou-agent\data`？

A：这样仓库边界更清楚。代码和文档在 `D:\juzhou-agent\peixun`，运行数据、SQLite、JSONL、向量索引和清洗资料在仓库外，避免误提交，也避免让项目看起来依赖旧的 OpenClaw 数据目录。

## 3. Agent 架构

### Q11：项目里的 skill 是什么？

A：skill 是 Agent 可执行的业务能力。网页端当前有创建培训草稿、查进度、删除培训记录、生成营销软文、知识库答疑、多语言翻译、普通聊天等内部 skill；OpenClaw 插件保留 8 个 training tool。

### Q12：Agent 怎么决定调用哪个 skill？

A：当前策略是快速 LLM Router 优先。本地规则不再作为业务意图的首选解释器，而是负责三件事：删除、发布、回滚等高风险动作必须确认；Router 不可用或低置信时兜底；知识库答疑和软文生成必须经过知识库选择与 RAG 证据校验。这样“生成英文文章并附中文翻译”会走软文生成，而“翻译成英文：这是一台水泵”才走翻译。

### Q13：模型意图判错怎么办？

A：后端不会让模型直接执行高风险动作。低置信或高风险意图会返回确认卡片；删除、发布、回滚、恢复等动作还要通过 Tool Registry 的确认策略。轨迹评测会验证“不该调工具时不能调”。

### Q14：为什么“重新输入”不能直接发布？

A：用户重新输入完整培训安排时，语义上是在修正草稿，不是确认旧草稿。系统只把“确认发布/可以/发吧”等短确认语当成发布触发。

### Q15：删除培训记录为什么必须确认？

A：删除是高风险不可轻易撤销的动作。即使命中删除意图，也必须先展示确认卡片或校验确认 token，防止普通聊天或误判造成数据丢失。

### Q16：Tool Registry 解决什么问题？

A：它把 skill/tool 的名称、用途、风险等级、是否需要确认、幂等性、超时和执行入口统一登记。这样 HTTP 和 WebSocket 不需要各写一套分支逻辑，安全策略也不会散落在多个 controller 里。

### Q17：Agent Run 和 Trace 有什么区别？

A：Trace 是脱敏摘要日志，方便快速排查；Agent Run 是结构化运行记录，一次请求一个 run，里面按 step 记录记忆召回、意图路由、确认校验、skill 执行、结果输出和错误，更适合做轨迹评测和治理。

## 4. RAG 原理

### Q18：RAG 是什么？

A：RAG 是 Retrieval-Augmented Generation，先从知识库检索相关资料，再把资料作为上下文交给大模型生成答案。它的重点是让模型基于企业已有资料回答，而不是凭记忆编。

### Q19：用户一句话怎么匹配资料？

A：系统会把用户问题转换成检索 query，同时用 BM25 做关键词/型号/参数精确召回，用向量检索做语义召回，再融合排序。命中的是 child chunk，生成时展开到完整 parent context。

### Q19-1：老板端聊天怎么自动转成 RAG 答疑？

A：先由快速 LLM Router 判断是不是资料答疑，再由规则层做知识库别名、会话上下文和 RAG 命中校验。比如“请帮我检索 CM2 的相关知识”应选择银嘉泵/水泵知识库；水泵问答后追问“有具体型号吗”要沿用上一轮水泵资料库；“这是水泵，不是电机”不能切到电机资料库。通过校验后才调用 `answer_knowledge_question`，返回 `knowledge_answer`、知识库名、检索模式、来源和命中片段；用户点“当普通聊天”时仍可用 `forceGeneralChat` 跳过探测。

### Q19-2：为什么把 Tavily 做成六条生成链路的可选项？

A：本地知识库适合企业内部资料、产品参数和培训内容这类确定事实，但软文、讲义、考试解释、翻译术语和普通聊天有时需要公开背景资料。现在六条 LLM 生成链路都支持显式开启 `webSearchMode: "on"`：知识库答疑、营销软文、培训材料/发布生成、员工考试生成、多语言翻译和普通聊天。默认关闭，开启后才调用 Tavily Search API，把网页标题、URL、摘要作为第二类参考资料放进 prompt。设计上本地 RAG 或用户原文仍然优先，Tavily 结果不写入知识库、不做 embedding、不改变 RAG 评测口径；考试题的正确答案不能依据网页独有事实，翻译不能改变原文含义，普通聊天也会明确网页内容不可靠且不能执行网页指令。未配置 key、超时或搜索失败时，系统只追加 warning，继续走原生成链路。

### Q20：为什么要 BM25 + 向量混合检索？

A：embedding 擅长语义相近问题，但型号、功率、能效、条款号、标准号这类精确词容易被稀释。BM25 能精确召回专有词，向量能召回口语化表达，混合后更稳。

### Q21：什么是 Parent-Child RAG？

A：child chunk 小，适合搜索；parent chunk 大，保留完整业务语义，适合生成。搜索命中 child 后，系统用 parent 作为最终上下文，避免模型只看到半句参数或被切散的表格行。

### Q22：当前切片怎么避免业务语义被切散？

A：电机资料按标题、知识点、型号、系列、表格行和结构部件切父块；child 只承担检索。对于法律、合同等强条款资料，后续应增加专门规则，避免把“第三条第二款”和“第三条之二”混在一起。

### Q23：为什么不把 chunk 直接调大？

A：大 chunk 召回噪声高，模型上下文也更容易塞入无关内容。Parent-child 的思路是“检索小、生成大”：小块负责命中，大块负责完整语义。

### Q24：如何避免 RAG 噪声？

A：导入时清洗目录、页眉页脚、OCR 占位和低价值短片段；检索时使用 BM25 + 向量融合、低价值过滤和 parent 去重；生成时要求来源引用，资料不足则拒答。

### Q25：RAG 评测看什么指标？

A：当前默认看 retrieval-only 的 Top1、Top3 命中率、hybrid 是否不低于 BM25、分类命中和失败用例。大模型回答质量可以额外评估，但不作为检索回归的默认硬门槛。

## 5. Embedding 与模型部署

### Q26：BGE-M3 为什么说是现成模型？

A：BGE-M3 是已经训练好的通用 embedding 模型，直接拿来把 query 和资料 chunk 转成向量即可。10MB 级别企业资料通常不需要训练模型，重点是清洗、切片和评测。

### Q27：10MB 文本要训练 BGE-M3 吗？

A：不需要。10MB 更适合做 RAG 数据入库和索引，不适合拿来训练 embedding 模型。训练不仅成本高，还可能不如现成模型稳定。

### Q28：本地部署模型会不会更快？

A：小模型做意图或 embedding 可能更快，但长文本生成在普通服务器上未必快。当前策略是服务器可只跑 Ollama `bge-m3` 做 query embedding，聊天和生成仍走在线 API。

### Q29：为什么本地生成向量索引后上传服务器？

A：资料侧 embedding 可以离线批处理，本地机器资源更充足。服务器只需要用同一模型生成用户 query embedding，再和上传的 `vector-index-bge-m3.json` 做相似度匹配。前提是服务器的 chunks/chunkParents 与索引完全匹配。

## 6. 资料导入与视觉 PDF

### Q30：导入管理页解决什么问题？

A：它让非程序员也能上传资料、查看质量、触发导入任务、看 embedding 进度、查看版本差异和回滚，不再完全依赖命令行。

### Q31：为什么要做异步任务队列？

A：导入、embedding、回滚都是长任务。放到任务中心后，页面能看到真实阶段和错误，服务重启也能恢复 queued/running 状态，不再用同步请求假装进度。

### Q32：知识库版本管理有什么价值？

A：同名导入可能覆盖资料。保留当前版和上一版，可以查看新增、删除、变更文档，并在导入结果不理想时异步回滚，不影响任务、邀请、考试或记忆。

### Q33：图片型 PDF 没有 OCR 怎么补入知识库？

A：当前做法是本地把 PDF 渲染成页面图片，由人工式视觉阅读识别可读内容，整理成结构化 Markdown，再重新导入和重建向量索引。型号参数表会按“系列 -> 型号 -> 参数行”整理，例如银嘉泵目录里的 VM22、QB60、WZB750 等可以进入型号级检索。它不调用外部 OCR API，也不运行 Tesseract/PaddleOCR；看不清的内容不猜。

### Q34：这类视觉补全的局限是什么？

A：它适合少量关键资料补全，不适合大规模自动化处理。如果后续资料量很大，应接入正式 OCR、版面解析和表格识别流水线。

## 7. 记忆模块

### Q35：项目里有记忆模块吗？

A：有。本地记忆包括短期会话、长期偏好和工作流经验，存储在 SQLite 或 JSON 回滚文件中；完整聊天历史继续写 JSONL。

### Q36：记忆会不会影响事实准确性？

A：不会把记忆当产品事实库。记忆只能补默认偏好，例如软文风格或默认题数；产品参数、卖点和答案必须来自知识库 RAG。

### Q37：怎么避免乱记或记住敏感信息？

A：记忆策略会过滤 API Key、联系方式、成绩评价、删除/发布偏好等敏感或高风险内容。模糊记忆先作为 pending 候选，需要用户确认。

### Q38：用户当前输入和记忆冲突怎么办？

A：当前输入优先。记忆只在用户没有明确说明时补默认值，不能覆盖本轮指令。

## 8. 数据与存储

### Q39：为什么从 state.json 迁移到 SQLite？

A：JSON 文件适合 MVP，但数据增长后写入冲突、查询效率、备份一致性和任务/记忆扩展都吃力。SQLite 仍然轻量单机，但更可靠，适合当前本地部署阶段。

### Q40：SQLite 是最终数据库吗？

A：不是。它适合当前单机和低并发部署；如果未来做多租户 SaaS，需要 PostgreSQL、对象存储、权限系统和审计能力。

### Q41：为什么仍保留 JSON？

A：为了兼容旧数据、导出备份和回滚。`state.json meta.version = 1` 继续保留，SQLite 内部 schema 单独演进。

### Q42：备份恢复怎么做？

A：`backup:data` 使用 SQLite backup API 生成一致快照，并打包 JSONL、向量索引和 JSON 兼容副本；可以传 `--retention-days` 和 `--keep-last` 清理旧备份，但只会删除带钜洲备份 manifest 的 ZIP。`restore:data` 必须带 `--force`，恢复前自动备份当前数据。

## 9. 安全与可靠性

### Q43：项目如何防止模型乱编？

A：RAG 上下文必须来自知识库；低质量和占位 chunk 会被过滤；资料不足时拒答；输出保留来源引用；RAG 评测会检查命中和来源。

### Q44：高风险动作如何处理？

A：发布、删除、知识库回滚、恢复、清空记忆等动作都需要确认。低置信意图返回确认卡片，后端 Tool Registry 再做风险校验。

### Q45：公网部署有哪些安全不足？

A：当前 `TRAINING_ACCESS_KEY` 不是完整账号体系。公网使用时应增加 HTTPS、反向代理、访问控制、防火墙、日志脱敏、备份策略和更细粒度权限。

### Q46：Trace 会不会泄露聊天或 Key？

A：Trace 和 Agent Run 只保存 message preview、hash、意图、skill、action、耗时和错误等摘要，不保存完整 API Key 或完整模型输出。

### Q47：如果模型 API 不可用怎么办？

A：普通聊天、翻译和生成类任务返回明确错误；操作类意图仍可本地识别，但需要模型生成的讲义、试题、软文或翻译结果不会伪造。

### Q47-1：线上服务怎么保证长期运行？

A：当前 Windows Server 不额外引入 PM2、NSSM 或 Docker 进程管理，而是使用计划任务。主任务 `JuzhouAgentTraining` 以 `SYSTEM` 运行 `start-server.ps1`，把 `ExecutionTimeLimit` 改成 `PT0S`，避免 72 小时自动终止，并配置 1 分钟间隔的短失败重启。第二个任务 `JuzhouAgentTrainingWatchdog` 每 5 分钟检查 8787 端口、首页和 `/api/health`，如果端口或 HTTP 不通就停止异常主任务并重新启动。第三个任务 `JuzhouAgentTrainingBackup` 可每天运行 `backup-server.ps1`，生成并校验运行数据备份，默认保留 14 天且至少保留最近 10 份。第四个任务 `JuzhouAgentOllama` 用 `start-ollama.cmd` 以 SYSTEM 启动本机 `127.0.0.1:11434` 的 `Ollama/bge-m3`，只给训练服务做 query embedding，不对公网开放。`/api/health` 未带密钥返回 `401` 是正常鉴权。启动脚本追加 `logs/server.log`，watchdog 写 `logs/watchdog.log`，备份写 `logs/backup.log`，Ollama 写 `logs/ollama-system.log`，方便判断是正常退出、崩溃、被系统杀掉还是备份失败。

## 10. 交互体验

### Q48：为什么前端曾经显示 `**加粗**`？

A：大模型输出 Markdown，前端如果按纯文本渲染就会看到 `**`。解决方式是增加安全 Markdown 渲染或有限格式解析，同时继续走 `escapeHtml`，避免 XSS。

### Q49：为什么做 WebSocket 流式输出？

A：讲义、软文、普通聊天可能生成较慢。流式输出可以实时更新模型文本，并展示阶段状态，减少“页面卡住”的感觉。现在普通聊天只有收到 `done` 才算完整结束；如果 WebSocket 在 `done` 前断开，前端会保留已收到内容并提示“连接提前中断”，不会把半截回答静默当成成功。OpenAI-compatible 的流式和结构化 JSON 生成都会透传 `finish_reason=length`，提示回答达到模型输出上限、可能不完整；软文正文清洗层不再固定裁到 1800 字符，避免后端主动追加省略号。

### Q50：进度条能显示大模型真实思考进度吗？

A：不能精确知道模型内部思考进度。项目里适合显示阶段进度，例如意图识别、检索资料、生成内容、保存结果，而不是伪造百分比。

### Q51：为什么把聊天记录从本地侧边栏迁到服务端？

A：本地侧边栏只能覆盖单浏览器体验，老板换电脑后看不到历史。当前设计改为服务端会话历史：前端请求携带 `sessionId`，后端按固定的 `boss-default` 账号把 user/assistant turn 写入 SQLite 的会话表；同一服务和数据目录下，不同浏览器或电脑可以读取同一批会话。左侧会话列表按最后一条真实消息的 `lastMessageAt` 倒序，旧的 `lastMessageAt/updatedAt` 污染会按消息记录修复；GET 查看、PATCH 重命名或前端恢复渲染不会把旧会话顶到最前，只有追加新消息才会前移。旧 `localStorage` 记录需要用户确认后导入，并只保存为去 HTML/script 的安全文本 transcript。

### Q51-1：删除一条老板端聊天会不会删业务数据？

A：不会。聊天会话和培训业务状态是分开的。删除聊天会话只隐藏或删除该会话历史，不删除 `tasks`、`invites`、`quizzes` 或本地 `memories`。这是为了避免用户整理聊天列表时误删已经发布的培训、邀请链接、考试记录和记忆偏好。

## 11. 外部能力整合

### Q52：报价表适合整合吗？

A：适合，但应作为独立报价 skill，不应混入培训 RAG。报价涉及结构化表格、价格规则、客户条件和审批，最好单独建 schema、校验和确认流程。

### Q53：AlibabaPublishAssistant 适合整合吗？

A：适合做独立发布 skill，但风险比软文高。它会操作外部平台和商品信息，需要预览、确认、失败重试、素材校验和操作日志。

### Q54：视频生成器适合整合吗？

A：适合作为异步任务 skill。视频生成耗时长、产物大，应该走任务中心，不适合同步聊天请求。

### Q55：图片目录适合整合吗？

A：适合作为素材库或视觉检索能力，但不应直接当产品事实来源。图片说明、标签和引用关系要单独治理。

## 12. 测试与评测

### Q56：项目有哪些测试？

A：有语法检查、烟测、RAG 评测、意图评测、记忆评测、Agent 轨迹评测、Trace 评测、SQLite 评测、备份/恢复/保留策略评测、导入评测、任务评测、老板端聊天历史评测、WebSocket 流式输出评测、软文长度回归评测、软文去重回归评测、多语言翻译评测和知识库版本评测。

### Q57：轨迹评测和意图评测区别是什么？

A：意图评测看“分类对不对”，例如水泵宣传文章要进 `generate_marketing_article`，明确翻译才进 `translate_text`；轨迹评测看“整个执行路径对不对”，例如是否先确认、是否错误执行删除、是否把文章+翻译误走翻译工具、是否在 CM2 或追问型号时选对银嘉泵/水泵知识库。

### Q58：RAG 评测集怎么构造？

A：用真实资料中的业务问题构造，覆盖型号参数、结构原理、制造工艺、销售话术、多语言和标准资料。每条用例有 query、expected 和可选 minHits。

### Q58-1：多语言翻译评测怎么避免依赖真实模型质量？

A：`npm run eval:translation` 会使用临时 `TRAINING_DATA_DIR`、关闭认证，并启动本地 OpenAI-compatible mock 服务。评测重点不是译文文学质量，而是路由和接口契约：显式中英日西法目标语言、英文默认翻中文、中文默认翻英文、正文在前且翻译指令在末尾、长文本不静默截断、无正文返回 `translation_request`、有老板端上一条正文时复用上下文、LLM API 缺失时返回清晰错误、`翻译成英文：这是一台水泵` 能走翻译，以及“生成英文文章，同时附带中文翻译”不会被翻译 parser 抢走。

### Q58-2：服务器性能测试怎么做？

A：新增了 `server-audit:*` 审计脚本。生产端口只做只读基线，例如 `/api/auth/status`、`/api/health`、知识库、任务和 Agent Run 查询；极限压测放到同服务器隔离副本，使用独立 `TRAINING_DATA_DIR`、`TRAINING_SQLITE_PATH` 和端口，避免污染线上数据。压测脚本用 Node 原生 `fetch` 做阶梯并发，记录 RPS、错误率、p50/p95/p99 和资源采样；写入链路必须显式传 `--allow-write`。本轮服务器隔离副本测到读链路 20 并发内 0 错误，50 并发开始超时，100 并发错误率 35.43%；写链路 boss-chat create/delete 到 20 并发仍 0 错误。测试还跑通了培训发布、员工答疑、生成考试、提交答案、报表汇总、备份校验和 throwaway 恢复。

### Q58-3：怎么把测试结果沉淀成简历材料？

A：审计脚本统一输出 JSON 到 `server-audit-output`，再由 `npm run server-audit:report` 汇总成 `docs/PERFORMANCE_AUDIT.md` 和 `docs/RESUME_EVIDENCE.md`。报告里记录数据规模、功能回归、接口性能、并发稳定性、合成数据、bug 风险和证据文件；简历文档把这些数字改写成业务成果口径，例如“建立服务器级性能与稳定性审计体系，覆盖资料导入、RAG 检索、培训发布、考试提交、报表汇总和备份恢复”。本轮可以写的数字包括：隔离副本最大读压测 100 并发、20 并发稳定 0 错误、写链路最高 12.47 RPS、业务闭环全链路通过、备份 4.25 MB 并完成校验和恢复；Tavily 旧版答疑专项 5 个真实样本成功率 100%，on p95 8470 ms，平均 3.8 个知识库来源 + 4 个联网来源，5/5 个 API 透传用例通过，4/4 个异常降级场景保留本地 RAG。新版专项脚本增加六链路表，覆盖答疑、软文、培训材料、考试、翻译和普通聊天的 off/on 对比。历史 embedding 失败和 CSV direct 导入不覆盖继续作为风险记录，最新生产健康检查是 `ollamaOk=true`、`localVectorIndexOk=true`、`retrievalMode=hybrid`。

### Q58-4：Tavily 六链路联网专项怎么测？

A：分两层测。第一层是 `npm run eval:web-search` 的 mock 回归，用 mock Tavily 和 mock OpenAI-compatible LLM 覆盖六条链路：`webSearchMode:off` 不调用 Tavily，`on` 返回 `webSearchStatus=ok`、`webSources/webSourceRefs`，缺 key、Tavily 500、超时、空结果都不打断原生成链路；同时断言 prompt 已把“本地知识库资料/用户原文”和“联网搜索资料”分区，并明确禁止执行网页指令。第二层是服务器审计，“生产只读基线 + 服务器隔离副本端到端”：生产只读先确认 `/api/health`、部署代码、Tavily 配置存在性和知识库规模；隔离副本使用独立 `TRAINING_DATA_DIR`、端口和临时 access key。旧版结果是 5 个真实联网答疑样本成功率 100%，on 平均 6538 ms、p95 8470 ms，API 5/5 通过，异常降级 4/4 通过；新版脚本会额外输出六链路专项表和发布/考试生成 API 覆盖。

### Q58-5：embedding 后端为什么不可用，后来怎么恢复？

A：审计时 `/api/health` 显示 `ollamaOk=false`、`retrievalMode=bm25`，隔离副本 embedding 任务报 `fetch failed`。排查后确认不是代码找不到模型，而是服务器上 Ollama 没有持久运行：临时手动启动能监听 `11434`，SSH 会话结束后就消失；旧计划任务也没有把 `OLLAMA_MODELS` 和日志托管好。修复方式是在服务器新增 `JuzhouAgentOllama` 计划任务，用 `start-ollama.cmd` 固定 `OLLAMA_HOST=127.0.0.1:11434` 和 `OLLAMA_MODELS=C:\OllamaModels`，以 SYSTEM 后台运行。验证结果是 `/api/embed` 能返回 1024 维 bge-m3 向量，训练服务 `/api/health` 恢复为 `ollamaOk=true`、`localVectorIndexOk=true`、`retrievalMode=hybrid`。`qdrantOk=false` 在当前 local vector backend 下是正常的，因为 Qdrant 是可选高资源后端。

### Q59：为什么文档也要跟代码一起更新？

A：这个项目迭代很快，架构、部署、RAG、记忆和服务器策略经常变化。如果文档落后，后续开发和面试表达都会基于错误事实。当前同步的是 Markdown 项目文档和桌面 QA 镜像；本轮不做 Word 导出。

## 13. 面试追问

### Q60：项目最大难点是什么？

A：不是单个 API 调用，而是把 RAG 资料质量、Agent 工具选择、安全确认、业务状态、异步任务和可观测性放到一个可维护闭环里，并保证模型失败时不会假装成功。

### Q61：你个人贡献怎么描述？

A：可以说负责从 MVP 到可维护 Agent 架构的重构，包括后端分层、domain 拆分、AI 层拆分、前端模块化、DeepSeek 接入、快速 LLM Router 与安全门禁、WebSocket 流式、RAG 混合检索、Parent-Child、SQLite、记忆、任务中心、Trace/Agent Run、导入版本回滚、服务器性能审计和评测体系。

### Q62：项目当前不足是什么？

A：账号权限还比较简单；OCR/版面解析还不是自动化平台；SQLite 不是多租户数据库；部分业务 skill 如报价、阿里发布、视频生成还未正式接入；公网安全和审计还需要加强。

### Q63：如果继续优化，优先做什么？

A：优先补账号权限和公网安全、备份失败告警与异地副本、资料治理自动化、报价/发布等独立 skill、更多轨迹评测、服务器性能趋势看板和线上质量监控。

### Q64：软文 skill 的内容是什么？

A：软文 skill 的内部名称是 `generate_marketing_article`，属于网页端业务 skill，不是 OpenClaw 插件里的 8 个 training tool。它的作用是把“写软文、宣传文章、官网文章、独立站文章、B2B 文案、产品介绍、推广文案”等自然语言请求，转成一个基于本地知识库的营销文章生成流程。

它主要包含几部分：

1. 意图识别：本地规则和快速 LLM Router 都会识别软文类表达；“英文文章、三篇文章、附带中文翻译、中英双语”这类需求仍归到软文 skill，而不是被纯翻译 skill 抢走。
2. 知识库匹配：根据用户输入里的水泵、电机、品牌、型号、资料库名称等信息，选择最相关的本地知识库。比如水泵请求不能误选电机资料库。
3. RAG 检索：对匹配到的知识库做混合检索，取相关 parent context 作为文章依据。
4. 可选联网：默认不做互联网搜索；用户显式开启 `webSearchMode: "on"` 时，Tavily 结果只作为外部市场/背景参考，产品事实、参数和卖点仍以本地知识库为准。
5. 资料不足拒绝生成：没有匹配知识库或没有足够相关 chunk 时，返回“资料不足，无法生成软文”，不编造产品参数。
6. 结构化生成：调用大模型输出 JSON，兼容旧的单篇 `article` 字段，同时新增 `articles[]`，支持多篇文章按应用场景型、采购决策型、技术卖点型、维护成本型、客户沟通型等角度差异化生成。
7. 去重复率和 AI 写作痕迹闭环：首轮生成后计算单篇内部重复、同批最高相似、最近 3 天历史软文最高相似、标题相似、模板句命中和 `aiWritingScore`；默认阈值分别是 `0.18`、`0.42`、`0.50`、`0.65`、模板句不超过 `2`、AI 写作痕迹分不超过 `35`。不达标时自动重写，默认最多 2 轮。
8. 写作约束：文章面向客户营销，默认适合官网、公众号、B2B 平台；有转化感，但不能夸大、不能写资料外事实、不能假装引用外部市场数据。prompt 还要求减少通用 AI 模板感、空泛套话、万能开头、过度排比和口号式结尾，并接入固定版本 `conorbronsdon/avoid-ai-writing` detector 识别英文 AI-isms、模板转场、夸张营销词和 chatbot 式客套，让首轮输出更像工业品业务人员或内容编辑写给真实客户看的文章。
9. 偏好记忆：如果用户长期偏好里有“软文短一点”“偏公众号”“偏 B2B”等设置，会作为默认值；但本轮用户明确要求优先。
10. 前端展示：老板端聊天里渲染为“营销软文”卡片，展示标题、摘要、核心卖点、正文、资料来源、联网来源、检索模式、模型、警告和“重复率 / AI 写作痕迹”指标。
11. 运行记录：执行过程会进入 Agent Run / Trace，记录意图、skill、action、文章数量、来源数量、重复率状态、AI 写作痕迹分、重写次数、警告数量、检索模式和模型信息。

面试里可以这样说：

> 软文 skill 不是简单套一个写作 prompt。它先通过意图路由识别营销文章请求，再匹配本地知识库，走 RAG 检索拿到来源片段；如果用户显式开启联网搜索，再用 Tavily 补充外部市场/背景参考，最后调用大模型输出结构化文章。为了避免幻觉，我把本地资料设为产品事实主依据，没有资料就拒绝生成，网页资料只作参考，冲突时不能覆盖企业资料。为了降低重复率和 AI 味，我又加了自动检测和重写闭环：多篇文章会分配不同角度，首轮生成后计算内部重复、同批相似、最近 3 天历史相似、标题相似、模板句命中和 avoid-ai-writing 的 AI 写作痕迹分，不达标默认最多重写 2 轮；测试夹具里三篇高度相似稿触发 1 次重写后，同批最高相似度从高风险降到约 1.9%，历史最高相似度约 5%，AI-heavy 英文样本 78 分能被拦截，重写后最终 AI 写作痕迹最高分 0。重写只能改表达和结构，不能编造新卖点或新参数。
