# Agent 项目面试 QA

更新时间：2026-05-26  
适用项目：钜洲培训 Agent / 企业业务 Agent 原型  
维护约定：后续如果继续讨论项目架构、技术选型、RAG、意图识别、报价、发布、视频生成等内容，应及时把适合面试表达的问题和回答补充到本文档。

## 1. 项目定位

### Q1：这个项目到底是 Agent 项目还是 RAG 项目？

A：更偏向 Agent 项目，RAG 是其中的核心能力模块之一。

这个项目不是单纯的“文档问答系统”，而是一个面向企业培训、营销、报价和发布场景的业务 Agent。它会先理解用户意图，再把任务分发到不同 skill，比如培训发布、培训进度查询、删除培训记录、营销软文生成、普通聊天等。RAG 主要负责从本地知识库中检索资料，为讲义生成、答疑、考试出题和软文生成提供依据。

可以概括为：

```text
业务 Agent 外壳
  -> 意图识别
  -> skill 路由
  -> 工具调用
  -> 人工确认
  -> RAG 检索增强生成
```

### Q2：如果面试官问项目亮点，应该怎么说？

A：可以从业务闭环和工程落地两个角度说。

业务上，它不是一个 demo 聊天机器人，而是把企业内部资料变成可执行流程：管理员用自然语言创建培训，系统基于资料生成讲义和考题，员工通过专属链接学习考试，管理员再查看完成率、平均分和薄弱知识点。

工程上，它有几个重点：

- 本地资料清洗、业务语义切片、Parent-Child RAG、混合检索和来源引用。
- 混合意图路由：本地规则 + LLM router + 置信度门控。
- 高风险操作确认，比如删除培训记录。
- WebSocket 流式输出，提升聊天体验。
- 本地记忆模块，用于普通聊天连续性和低风险默认偏好。
- 保持可独立部署，不强依赖 OpenClaw。
- 后续可扩展报价、阿里发布、视频生成等业务 skill。

### Q3：为什么不直接说这是一个 LMS 或 OA 系统？

A：因为当前项目重点不是账号体系、组织架构、权限审批、课程商城这些完整 LMS/OA 能力，而是企业内部知识资料到培训闭环的 AI 工作流。

更准确的说法是：

> 面向企业培训和营销场景的轻量级业务 Agent，内置 RAG 知识检索和多 skill 工作流编排能力。

## 2. 技术选型

### Q4：为什么后端使用 Node 原生 HTTP，而不是 Express/Fastify？

A：这个项目当前是轻量 MVP，接口数量可控，核心复杂度在 AI 编排、RAG、业务流程和数据质量，而不是 Web 框架。使用 Node 原生 HTTP 可以减少运行时依赖，便于打包和在 Windows 环境部署。

重构后通过 `src/http` 层拆分请求解析、响应 helper、认证、静态文件、API 路由和 controller，避免把所有逻辑堆在 `server.mjs` 中。这样即使不用 Express，也能保持清晰分层。

### Q5：为什么前端不引入 React/Vue？

A：当前界面主要是一个老板端聊天窗口和员工端学习/考试页面，交互复杂度还没到必须使用前端框架的程度。使用无构建 ES modules 可以降低部署复杂度，直接通过浏览器加载模块。

前端拆分为 API、认证、聊天端、员工端、渲染器、DOM 工具等模块，保持代码可维护，同时不引入构建链。

### Q6：为什么使用 DeepSeek API，而不是本地模型？

A：长文本生成、讲义生成、出题和软文生成对模型质量要求较高，在线大模型通常比普通本地设备更稳定。对于这个项目，本地模型不一定更快，尤其是长上下文和复杂生成任务。

更合理的方案是混合：

- 本地规则或小模型做意图识别。
- 本地 RAG 做资料检索。
- 在线大模型做最终生成。

### Q7：为什么删除 fallback？

A：因为培训讲义和考试题不能靠兜底模板假装生成。用户已经明确要求：没有 API 就不生成讲义、不出题。

这样做牺牲了一点“看起来可用”的体验，但保证内容可信。对于培训、考试、报价这类业务，编造内容的风险比失败提示更高。

### Q8：OpenClaw Gateway 在项目里有什么用？

A：OpenClaw Gateway 是可选的 Agent/工具调用入口。项目可以通过 OpenClaw 插件暴露 8 个 training tool，让外部 Agent 调用培训系统能力。

但当前 training-service 可以独立运行。没有 OpenClaw Gateway 时，网页端仍然可以通过本地 API 和 DeepSeek API 工作。OpenClaw 更像外部编排入口，不是项目运行的必要条件。

### Q8-1：OpenClaw Gateway 现在还有存在意义吗，要不要删掉？

A：短期不建议直接删除，建议降级为可选适配器。

现在项目已经可以通过 OpenAI-compatible API 直连 DeepSeek，核心培训、软文、问答和出题不再必须依赖 OpenClaw Gateway。但 Gateway 仍有两个价值：一是兼容历史 OpenClaw 插件和 8 个 training tool，二是保留未来接入外部 Agent 编排的入口。

更合理的处理方式是：

- 主路径使用 direct LLM，也就是 DeepSeek/OpenAI-compatible API。
- OpenClaw Gateway 只作为可选 provider。
- 文档里明确它不是必需依赖。
- 如果长期不再使用 OpenClaw 插件，再做一次独立删除。

这样既能减少运行时困惑，又不会过早切断历史兼容能力。

### Q8-2：为什么把数据从 OpenClawData 迁到 juzhou-agent\data？

A：这是为了让项目边界更清楚。早期项目借用了 OpenClaw 的目录和运行习惯，业务资料、向量索引、SQLite 数据库和 trace 文件放在 `D:\OpenClawData`，容易让人误以为培训系统必须依赖 OpenClaw 主仓库。

迁移后源码在 `D:\juzhou-agent\peixun`，运行数据在 `D:\juzhou-agent\data`。服务默认从项目根推导数据目录：`training-index` 保存 `training.db`、JSON 回滚文件、聊天日志、Agent Run、任务队列和本地向量索引；`training-raw`、`training-clean`、`training-vision` 保存导入资料和清洗产物。

这样项目可以独立部署、独立备份、独立迁移。OpenClaw 插件仍保留，但只是外部 Agent 调用培训 API 的兼容层，不再是默认运行前提。

## 3. Agent 架构

### Q9：什么是 skill？这个项目里的培训是不是 skill？

A：是的。可以把培训能力看成一个内部 skill。用户输入自然语言后，Agent 先识别意图，再把任务交给对应 skill。

当前技能边界可以理解为：

```text
create_training_draft      创建培训草稿
show_training_status       查询培训进度
delete_training_records    删除培训记录
generate_marketing_article 生成营销软文
answer_general_chat        普通聊天
```

未来报价、阿里发布、视频生成也可以作为独立 skill 接入。

### Q10：为什么需要意图识别？

A：因为同一个聊天入口里有普通聊天和业务操作。如果不做意图识别，系统可能把“你是谁”误当成培训任务，也可能把“重新输入一条培训安排”误当成“确认发布旧草稿”。

意图识别的目标不是炫技，而是把用户话语安全地路由到正确能力。

### Q11：当前意图识别怎么做？

A：采用混合路由：

```text
本地规则
  -> LLM JSON router
  -> 结果归一化
  -> 置信度门控
  -> 确认卡片或执行 skill
```

本地规则负责高置信、低成本判断，比如明显的删除、查询进度、写软文。LLM router 负责模糊表达。低置信或高风险操作进入确认卡片。

### Q12：为什么删除培训记录要确认？

A：删除属于高风险操作，一旦误删会影响任务、邀请链接、考试结果和报表。因此即使命中删除意图，也先返回 `intent_confirm`，前端展示确认卡片，用户确认后才带 `confirmedSkill` 再请求服务端执行。

### Q13：为什么“重新输入：给李小红发布培训”不能直接发布？

A：因为这是新的完整业务指令，不是对旧草稿的确认。系统必须把它当作新草稿创建，而不是拿旧草稿发布。

当前规则收紧了发布确认，只有“确认发布”“可以”“发吧”等短确认语在已有草稿上下文中才会触发发布。

### Q14：普通聊天怎么处理？

A：普通聊天默认走大模型聊天，不再被宽泛关键词误拦截。只有明确命中业务意图时才进入 skill。

如果大模型 API 不可用，普通聊天会返回清晰错误；操作类意图仍可走本地规则和确认流程。

## 4. RAG 原理

### Q15：RAG 是什么？

A：RAG 是 Retrieval-Augmented Generation，检索增强生成。核心思想是：先从资料库里找证据，再把证据交给大模型生成答案。

项目中 RAG 用于：

- 培训讲义生成。
- 员工答疑。
- 考试题生成。
- 营销软文生成。
- 后续可扩展到报价和产品推荐。

### Q16：RAG 如何通过用户的话匹配资料？

A：流程是：

```text
用户问题
  -> 文本规范化
  -> 关键词检索 / 向量检索
  -> 合并和排序
  -> 过滤低质量片段
  -> 选出 top-k 上下文
  -> 交给大模型生成
```

关键词检索适合精确词，比如型号、产品名、参数。向量检索适合理解语义相近的表达。成熟系统通常使用混合检索。

### Q17：当前切片粒度是多少？

A：当前不是单纯按字符数切片，而是业务语义切片 + Parent-Child 结构。

```text
chunkParents：保存完整业务父块，如知识点、型号/系列、表格行
chunks：保存检索子块，带 parentId、childType、businessKeys、searchText
普通 child 默认上限约 720 字符，重叠约 60 字符
```

Markdown 会优先按标题/章节形成父块；表格行和型号参数尽量保持为完整父块；非 Markdown 或无法识别结构的资料才走兼容切片兜底。

已重建的电机培训知识库里，最长子块从原来的 3000+ 字符降到约 720 字符。这个数字是当时重建后的验证结果，不代表所有未来资料都会自动保持这个长度，后续导入新领域仍要看质量报告。

### Q18：业务语义还会不会被切散？

A：风险已经比纯字符切片低很多，但没有完全消失。

当前电机资料会按知识点、型号/系列、表格行形成父块，再用子块检索、父块生成。这样能避免“型号、能效、级数、功率范围”被切到不同上下文里。

但如果后续导入法律文档、报价规则、合同条款等新领域，还需要增加对应领域规则。例如法律里的“第三条第二款”和“第三条之二”不能按普通数字或标题粗暴合并，否则会改变含义。

### Q19：怎么避免业务语义被切散？

A：项目已经采用业务语义切片，核心做法是：

- 产品资料按型号切。
- 报价表按可报价单元切。
- 培训资料按知识点切。
- 售后资料按故障案例切。
- 表格按行、表头、型号、配置关系切。

并且给子块加 metadata：

```json
{
  "parentId": "parent-xxx",
  "childType": "model_spec",
  "businessKeys": {
    "model": "YE3",
    "efficiency": "IE3",
    "poles": "4",
    "powerRange": "0.75-315kw"
  },
  "searchText": "包含来源、标题、业务字段和子块内容"
}
```

### Q20：什么是 Parent-Child Retrieval？

A：它的思想是“小块检索，大块返回”。

子 chunk 用来做精准匹配，比如参数、卖点、价格、应用场景。父 chunk 保存完整业务对象，比如一个产品型号、一条报价规则、一整个故障案例。

检索时命中子 chunk，但生成时返回父 chunk，避免模型只看到半截信息。

### Q21：什么是 Contextual Retrieval？

A：Contextual Retrieval 是给每个 chunk 补充上下文头，让孤立片段更容易被检索。

例如普通 chunk 是：

```text
功率范围 0.18-315kw，IE1，铁壳。
```

补充上下文后变成：

```text
这是电机数据汇总表中 Y2 系列三相异步电机的参数，机壳为铁壳，能效 IE1，功率范围 0.18-315kw。
```

这样 embedding 和关键词检索都会更准。

### Q22：如何提升 RAG 精度，避免噪声？

A：优先级可以这样排：

1. 文档清洗，去掉 OCR 占位、页眉页脚、目录、无意义短片段。
2. 业务语义切片，而不是纯字符切片。
3. BM25 + 向量混合检索。
4. 加 reranker，多召回后重排。
5. 加 metadata filter，比如产品型号、资料类型、业务实体。
6. 做置信度门控，资料不足就拒绝生成。
7. 建立固定 RAG 评测集，看 Top1/Top3 是否命中正确资料。

### Q23：为什么不直接把 chunk 调大？

A：chunk 太小容易丢上下文，chunk 太大容易引入噪声。直接调大不是根本方案。

更好的方案是：

```text
业务对象完整保存
检索片段精细化
返回上下文完整化
```

也就是小块召回，父块生成。

## 5. Embedding 与模型

### Q24：BGE-M3 为什么说是现成的？

A：因为它是已经预训练好的开源 embedding 模型，可以直接把文本转成向量，不需要用自己的 10MB 文本重新训练。

项目里真正要做的是：

```text
资料清洗
  -> 切片
  -> 用 BGE-M3 向量化
  -> 存入向量索引
  -> 查询时匹配相近向量
```

### Q25：10MB 文本需要训练 BGE-M3 吗？

A：通常不需要。10MB 文本量不大，优先做向量化入库即可。

真正微调 embedding 模型需要构造 query、positive、negative、hard negative 等训练样本。多数情况下，RAG 效果差不是因为 BGE-M3 没训练，而是切片、清洗、metadata、检索策略和重排没做好。

### Q26：本地部署模型会不会比在线 API 快？

A：不一定。小模型做意图识别可能更快，但长文本生成、讲义生成、出题、软文生成如果用普通本地硬件，可能比 DeepSeek API 更慢，质量也可能下降。

推荐方案是：

```text
本地规则/检索
  + 在线大模型生成
```

## 6. 流式输出与交互

### Q27：为什么要做 WebSocket 流式输出？

A：大模型生成长文本时，如果等完整结果返回，用户会感觉系统卡住。WebSocket 可以把模型输出片段实时推给前端，聊天窗口边生成边更新。

这对普通聊天、软文生成、讲义生成尤其有用。

### Q28：进度条能不能显示大模型思考进度？

A：不能准确知道大模型内部思考进度。可行的是显示阶段进度，比如：

```text
识别意图
检索资料
生成内容
整理结果
完成
```

这不是模型真实 token 进度，而是业务流程进度。它能让用户知道系统没有卡死。

## 7. 营销软文功能

### Q29：软文生成功能怎么设计？

A：它作为独立 skill，不和培训发布混在一起。

流程是：

```text
识别软文意图
  -> 匹配相关知识库
  -> RAG 检索产品参数、卖点、场景、质量信息
  -> 调 DeepSeek 生成文章
  -> 返回标题、摘要、正文、卖点、来源、风险提示
```

当前不接联网搜索。如果用户要求联网查资料，会提示当前版本未开启联网搜索，只基于本地资料生成。

### Q30：为什么资料不足时不生成软文？

A：因为营销文章如果编造参数、型号或应用场景，会影响客户信任。资料不足时应该明确提示，而不是让模型凭空写。

## 8. 外部能力整合

### Q31：报价表适合整合吗？

A：非常适合优先整合。报价表目录不是单纯 Excel，而是一个完整报价系统，有 Spring Boot 后端、H2 数据库、报价 API、泵产品、配件、价格、报价单和 Excel 导出。

它适合做报价 skill：

- 查询某型号价格。
- 生成报价单。
- 推荐配置。
- 生成销售话术。
- 为软文提供真实参数和价格依据。

### Q32：报价系统应该怎么接？

A：推荐保留它作为独立服务，Agent 通过 HTTP API 调用它。不要直接把 Java/Spring Boot 改写进 Node 项目。

合理架构：

```text
Agent 主服务
  -> quotation client
  -> 报价系统 API
  -> H2 / MySQL 数据库
```

这样可以降低耦合，报价系统坏了也不会拖垮培训系统。

### Q33：AlibabaPublishAssistant 适合整合吗？

A：适合，但不要深度合并。它是阿里国际站半自动发品执行器，依赖浏览器登录状态、Playwright、图片银行、页面结构和人工确认。

推荐做成发布 skill：

```text
Agent 生成商品内容
  -> 调用 Alibaba 发布助手
  -> 准备发布草稿
  -> 人工确认最终发布
```

不建议把浏览器自动化直接塞进主服务进程。

### Q34：视频生成器适合整合吗？

A：适合做营销素材生成 skill。它目前是 Python + FFmpeg 的本地视频生成器，适合根据产品图片和模板生成 15 秒产品展示视频。

推荐方式是 Agent 调用它的 CLI 或本地 Web API，返回视频路径和日志。

### Q35：图片目录适合整合吗？

A：目前不适合作为独立能力。当前图片目录更像图片恢复和竞品图片抓取脚本集合，不是稳定素材库。可以先作为 Alibaba 发布助手的辅助工具，暂时不要暴露成老板端主 skill。

## 9. 数据与存储

### Q36：为什么从 state.json 迁移到 SQLite？

A：`state.json` 在 MVP 阶段很适合快速验证业务闭环，但随着培训任务、邀请、考试、记忆和后续 skill 增加，JSON 文件会遇到并发写入、局部查询、备份恢复和数据校验的问题。

当前已默认接入 SQLite：`training.db` 保存业务状态和长期记忆，`state.json` 和 `memory.json` 保留为首次迁移来源和 `export:json` 回滚格式。这样仍保持本地部署简单，同时比单个 JSON 文件更可靠。正式多租户 SaaS 化时再考虑 PostgreSQL。

### Q37：记忆存储怎么实现？

A：当前把业务状态和 Agent 记忆统一迁移到 SQLite，但仍保持逻辑分层。

- `training.db` 保存知识库、任务、邀请、考试、报表、长期偏好、会话摘要、待确认记忆和记忆状态。
- `state.json` 和 `memory.json` 是旧版兼容文件，首次启动 SQLite 会自动导入，`npm run export:json` 可以重新导出。
- `conversation-history.jsonl` 追加完整聊天和工具调用摘要，按 `sessionId` 区分会话。

这些文件都放在 `TRAINING_DATA_DIR` 下，默认是 `D:\juzhou-agent\data\training-index`，不提交 Git。大量聊天历史继续放在 JSONL 里，避免把日志塞进主数据库。

## 10. 安全与可靠性

### Q38：项目怎么避免模型乱编？

A：主要靠几层约束：

- 没有 API 不生成讲义和试题。
- RAG 只传入检索到的本地资料。
- Prompt 要求只能基于给定资料回答。
- 答案带来源引用。
- 过滤 OCR 占位和低质量 chunk。
- 资料不足时拒绝生成。

### Q39：高风险操作如何处理？

A：高风险操作进入确认卡片，比如删除培训记录。后端不仅要求请求中带 `confirmedSkill`，还要求带服务端签发的 `confirmationToken`。这个 token 绑定原始消息和 skill，默认 15 分钟过期；如果缺失、过期、换消息或换 skill，后端都会拒绝执行。这样可以避免前端误触、模型误判或伪造确认导致真实数据被改动。

### Q39.1：如果模型把普通聊天误判成工具调用怎么办？

A：系统不会只凭模型判断就执行。当前是混合防误判链路：

```text
本地规则初判
  -> 可选 LLM router
  -> 置信度 / 风险门控
  -> 确认卡片或执行 skill
  -> 记录 agent trace
```

如果某个操作只由 LLM 识别、本地规则没有支持，会优先进入确认卡片。用户可以确认执行，也可以选择“当普通聊天”或“重新输入”。每次路由还会写入 `agent-traces.jsonl`，便于把真实误判样本补进 `eval:intent`。

### Q40：如果大模型 API 不可用怎么办？

A：普通聊天和生成类任务返回清晰错误，不使用假内容兜底。操作类意图可以继续通过本地规则识别，但真正需要模型生成的讲义、试题、软文不会生成。

## 11. 测试与验证

### Q41：项目怎么做回归测试？

A：目前主要有：

```powershell
npm run check
npm run eval:backup
npm run eval:sqlite
npm run smoke
npm run eval:rag -- --retrieval-only
npm run eval:intent
npm run eval:memory
```

`check` 检查语法，`eval:backup` 验证备份、校验和恢复链路，`eval:sqlite` 验证 JSON 导入、SQLite 读写、记忆迁移和 JSON 导出，`smoke` 跑核心业务闭环，`eval:rag` 验证检索效果，`eval:intent` 验证意图路由，`eval:memory` 验证记忆保存、召回、覆盖和敏感信息拦截。

### Q41-1：SQLite 接入后怎么做备份和恢复？

A：项目提供了三条命令：

```powershell
npm run backup:data
npm run backup:verify -- --from <backup.zip>
npm run restore:data -- --from <backup.zip> --force
```

备份默认放在 `TRAINING_DATA_DIR/backups`，包含 SQLite 一致快照、`state.json` / `memory.json` 回滚副本、聊天历史、路由轨迹和本地向量索引。恢复时默认只校验，必须加 `--force` 才覆盖；覆盖前会自动为当前数据再生成一份安全备份。

### Q42：为什么要单独做意图评测？

A：因为聊天入口的风险在于误判。一句话如果误判成删除、发布或生成旧草稿，会影响业务数据。意图评测可以固定覆盖培训发布、重新输入、确认发布、查进度、删除、软文和普通聊天等场景。

当前 `eval:intent` 覆盖 21 条样例，既有正例，也有容易误判的反例，例如“帮我看看培训应该怎么设计比较合理”必须走普通聊天，“删除知识库”不能误删培训记录，“联网查一下电机资料再写软文”只能进入软文 skill 并在生成阶段提示未开启联网搜索。

### Q43：RAG 评测看什么指标？

A：至少看：

- Top1 是否命中正确资料。
- Top3 是否包含正确资料。
- 是否混入无关 chunk。
- 是否返回 OCR 占位或低质量片段。
- 生成内容是否带来源。
- 资料不足时是否拒答。

当前项目的 `eval:rag -- --retrieval-only` 已扩展到 30 条固定问题，覆盖型号参数、结构原理、制造工艺、质量检测、销售话术、多语言资料和标准资料。检索评测不只看“有没有回答”，而是先看 Top1/Top3 是否命中正确父块，再看 hybrid Top1 是否不低于 BM25-only。这样可以及时发现两类问题：型号参数搜不准，或者语义问题被无关 chunk 抢占。

评测集构造原则是来自真实资料和真实业务问法：比如 `YE3 IE3 4级 功率范围` 检查表格行召回，`低压铸铝相比压力铸铝和离心铸铝有什么优势？` 检查工艺资料召回，`English IE3 motor IE3-90S-4 efficiency table` 检查多语言参数表召回。每条样例的 expected 关键词都来自本地知识库原文，避免为了通过测试编造答案。

## 12. 面试追问准备

### Q44：如果面试官问你最大的技术难点是什么？

A：不是调用大模型本身，而是让模型在真实业务资料上可靠工作。难点包括资料质量参差不齐、PDF/OCR/Excel 清洗、业务语义切片、检索噪声、意图误判、高风险操作确认，以及如何把 AI 输出接到真实业务流程里。

### Q45：如果让你继续优化，你会做什么？

A：优先做四件事：

1. 报价表结构化接入，形成报价 skill。
2. 在现有 BM25 + 向量混合检索后增加 reranker。
3. 完善 OCR 流程和资料质量提示。
4. 把培训、软文、报价、发布、视频统一成可配置 skill registry。

### Q46：这个项目和普通 ChatGPT 套壳有什么区别？

A：普通套壳主要是把用户消息转发给大模型。这个项目有业务数据、业务流程、意图路由、工具调用、确认机制、员工学习链接、考试提交、报表统计和 RAG 来源约束。大模型只是其中一个生成组件，不是全部。

### Q47：这个项目有什么不足？

A：可以诚实说：

- 当前持久化已升级为 SQLite，但仍是单机本地数据库，不适合直接包装成多租户 SaaS。
- 业务语义切片目前主要覆盖培训和软文资料，法律、报价、合同等新领域还要补领域规则。
- 当前没有完整企业账号权限体系。
- 报价、发布、视频生成还未完全接入。
- reranker 和更完善的向量检索还可以继续增强。

这类回答比过度包装更可信。

### Q48：如何描述你的个人贡献？

A：可以这样说：

> 我负责从 MVP 到可维护 Agent 架构的重构，包括后端分层、domain 拆分、AI 层拆分、前端模块化、意图识别混合路由、WebSocket 流式输出、RAG 检索质量优化、DeepSeek 接入、删除确认机制、营销软文 skill 和本地记忆模块的设计实现。同时补充了 smoke、RAG、intent 和 memory 评测脚本，保证重构后核心培训闭环可用。

### Q49：为什么要做业务语义切片，而不是继续按固定长度切 chunk？

A：固定长度切片实现简单，但容易把业务含义切散。比如电机资料里的型号、能效、级数、功率范围、表格行本来是一条完整业务记录，如果被切成几段，大模型拿到的上下文就可能缺字段，出培训讲义、考试题或营销软文时容易答偏。

业务语义切片的核心是按“知识点、型号、表格行”形成父块，再把父块拆成适合检索的小子块。这样检索时命中更精准，生成时又能拿到完整业务上下文。

### Q50：Parent-Child RAG 是怎么做的？

A：项目里采用“小 chunk 检索，大 parent 生成”的结构：

1. 导入知识库时先生成 `chunkParents`，保存完整业务语义父块。
2. `chunks` 继续作为检索子块，并带上 `parentId`、`childType`、`businessKeys`、`searchText`。
3. BM25 和向量检索都只搜索子块。
4. 命中子块后通过 `parentId` 展开到父块，多个子块命中同一父块时去重。
5. 培训讲义、员工答疑、考试出题和营销软文都使用父块上下文生成。

这样能同时兼顾检索精度和生成完整性：小块适合匹配用户问题，大块适合给大模型提供完整证据。

### Q51：这次 RAG 改造有什么可量化结果？

A：最新一轮对电机培训知识库做了两类改造：一是业务语义切片和 parent-child RAG，二是对图片型 PDF 做人工式视觉补全。重新导入 `D:\juzhou-agent\data\training-clean` 后，电机库为 15 个文档、184 个父块、213 个子块、表格行父块 42 个，最长子块 720 字符，且没有孤儿子块。本地 `bge-m3` 向量索引包含 204 个有效 chunk，动态质量评分为 98，OCR 占位数量为 0。

验证结果包括：

- `npm run check` 通过。
- `npm run smoke` 通过，培训发布、员工链接、答疑、考试、软文和删除记录仍可用。
- `npm run eval:rag -- --retrieval-only` 通过，评测集扩展到 30 条；本次结果 Top1 命中 29/30，Top3 命中 30/30，hybrid Top1 不低于 BM25-only 为 30/30。

### Q51-1：图片型 PDF 没有接 OCR，为什么还能补进知识库？

A：这里不是做自动 OCR，而是用项目内的 PDF 渲染脚本把 PDF 页面渲染成图片，再由 Codex 逐页视觉阅读可辨认内容，人工式整理成结构化 Markdown，最后重新导入知识库并重建本地向量索引。这个流程适合少量关键资料补全，比如本次的 `YINJIA motor catalog-2025.10.pdf`、`电机1-4.pdf` 和电机 3D 爆炸图。

它的原则是：能看清的产品系列、应用场景、铭牌字段、结构部件、工艺能力和销售卖点才写入；看不清或不确定的参数不编造。优点是不用外部 OCR 服务也能快速补齐关键资料，缺点是无法替代大批量自动 OCR 和版面解析。

### Q52：为什么要把检索策略从单纯 embedding 升级为 BM25 + 向量混合检索？

A：因为 embedding 擅长语义相似，但对型号、数字、功率范围、条款编号这类精确字段不一定稳。BM25 擅长精确词和参数召回，向量检索擅长语义召回，两者互补。

项目现在的检索流程是：BM25 和向量都检索 child chunk，然后把 BM25 分数和语义分数归一化融合；参数、型号、功率、能效类查询会提高 BM25 权重；命中后仍通过 `parentId` 展开父块给大模型生成。向量索引不可用时，系统会降级为 BM25，而不是退回旧的朴素关键词匹配。

### Q53：为什么要自己做本地记忆，而不是接 Mem0、Zep 或 Letta？

A：因为当前项目是本地部署 MVP，核心要求是少依赖、可控、易打包。外部记忆服务能力更完整，但会引入额外服务、账号、网络、数据合规和部署成本。

本项目先采用轻量自研：

```text
短期会话历史
  + 长期偏好记忆
  + 记忆提取策略
  + 敏感信息过滤
  + 用户确认/删除接口
```

这样能先满足普通聊天连续性、培训默认参数和软文风格偏好。当前长期记忆已随业务状态一起迁入 SQLite，后续如果业务规模扩大，再考虑 PostgreSQL 或专业 memory service。

### Q54：短期记忆和长期记忆怎么区分？

A：短期记忆解决“这轮对话上下文是什么”，长期记忆解决“用户长期偏好是什么”。

- 短期记忆：最近几轮老板端聊天、工具调用摘要、超长会话摘要。
- 长期记忆：用户明确说过“以后默认”的偏好，例如软文短一点、偏公众号、培训默认 10 道题 80 分。
- 工作流经验：用户纠正过的行为，例如“重新输入不是确认发布”。

生成时当前输入优先级最高。记忆只能补默认值，不能覆盖用户这次明确写出来的要求。

### Q55：怎么避免记忆乱记、偷记或记住敏感信息？

A：项目把记忆写入做成策略门控：

1. 显式“记住/以后/下次默认”的低风险偏好可以自动保存。
2. 模糊偏好先进入 `pending`，前端展示确认卡片，用户确认后才变成 `active`。
3. API Key、token、联系方式、员工成绩评价、删除/发布等高风险动作不会自动保存。
4. 用户可以“查看记忆”“删除这条记忆”“清空全部记忆”。
5. 清空全部记忆需要服务端确认 token，避免误删。

这套设计的重点不是让 Agent 什么都记，而是让用户能知道它记了什么，并且随时可改、可删。

### Q56：记忆会不会影响 RAG 的事实准确性？

A：不会把记忆当事实库。项目里明确区分：

- 记忆：用户偏好、输出风格、默认参数和工作习惯。
- RAG：产品资料、工艺参数、销售话术和培训依据。

例如用户记住“软文默认短一点，偏公众号”，它只影响文章长度和口吻；电机功率范围、工艺专利号、质量检测方法仍必须从 RAG 知识库检索出来。这样可以避免把用户偏好误当产品事实。

### Q57：为什么要做导入管理页面，而不是只保留命令行脚本？

A：命令行适合开发和批处理，但真实企业使用时，资料维护往往不是程序员完成的。导入管理页把“本机目录导入、浏览器上传、知识库质量检查、向量索引重建提示”放到老板端页面里，让业务人员能看到资料是否可用、哪里有 OCR 占位、是否需要重建向量索引。

实现上没有让页面和脚本各做一套逻辑，而是把清洗、语义切片和写库逻辑抽到 `src/import`，CLI 和 API 共用同一套服务。这样可以避免“网页导入”和“命令行导入”行为不一致。后来又把页面导入接入异步任务队列：导入后 BM25 立即可用，并自动创建本地向量索引子任务；embedding 失败不会回滚已导入知识库，而是在任务中心展示错误原因。

### Q58：为什么要做异步任务队列和 Agent Trace 可视化？

A：因为成熟 Agent 项目不只是“能调用模型”，还要能处理长任务、失败恢复和误判排查。

在这个项目里，导入资料和重建本地向量索引都可能耗时较长。如果直接在网页请求里同步执行，页面容易卡住，也无法清楚展示失败发生在哪个阶段。因此项目加入了本地异步任务队列：导入、清洗、语义切片、写库和 embedding 都作为任务执行，任务中心可以看到排队、执行、成功、失败、取消和错误原因。

Agent Trace 可视化解决的是另一个问题：模型或路由规则可能误判用户意图。Trace 页面展示脱敏后的消息预览、意图、skill、置信度、确认状态、action 和耗时，方便把真实误判样本补回 `eval:intent`，同时不暴露完整聊天内容或 API Key。

面试里可以这样概括：

> 我没有只做一个聊天入口，而是补了 Agent 运行态治理能力。长任务用本地队列管理，路由误判用 Trace 观测和评测集回归，这样项目从 MVP 更接近可运维的业务 Agent。

### Q59：为什么要做知识库版本管理和导入差异？

A：RAG 项目的资料不是一次性导入后就不变，真实业务里产品资料、表格参数、销售话术会不断更新。如果每次同名导入都直接覆盖旧 chunks，一旦新资料清洗质量差、误删文件或切片效果变差，就很难定位问题，也没有快速回滚能力。

本项目第一版采用轻量方案：每个知识库只保留 `current` 和 `previous` 两个完整快照，快照包含 `knowledgeBase`、`documents`、`chunkParents` 和 `chunks`，不包含任务、邀请、考试、记忆或日志。每次导入后按文档路径和内容 hash 生成文档级 diff，展示新增、删除、变更和未变文件。

回滚走异步任务队列，而不是同步改库：用户在导入页输入 `ROLLBACK` 后创建 `rollback_knowledge_base` 任务，回滚成功后自动创建当前知识库的本地向量索引重建子任务。这样 BM25 可以立刻使用，embedding 失败也不会影响已经恢复的知识库。

面试里可以强调这个取舍：

> 我没有一开始做无限版本审计，而是先保留上一版，解决最高频的“导入错了能看差异、能撤回”问题。这样既控制 SQLite 体积，又把资料治理能力接进了导入页面和任务中心。

### Q60：为什么又加 Agent Run，而不是只看 Trace 日志？

A：旧的 Trace 是“一次请求一条摘要”，适合快速看意图、skill、action 和错误，但它回答不了更细的问题：这次请求有没有读记忆、LLM 路由前本地规则是什么、确认 token 有没有校验、到底有没有执行删除工具、失败发生在哪一步。

Agent Run 把一次老板端请求拆成结构化 step，例如：

```text
memory_recall
memory_instruction
state_load
intent_route
confirmation_verify
tool_execute
memory_write
result_output
```

这样排查误判时可以直接看工具调用轨迹，而不是猜。SQLite 模式下 run 和 step 写入 `agent_runs` / `agent_steps`，JSON 回滚模式下追加到 `agent-runs.jsonl`。旧 `agent-traces.jsonl` 仍保留，并增加 `runId`，用于兼容已有 Trace 页面和测试。

### Q61：Tool Registry 在这个项目里解决什么问题？

A：之前网页端 skill 的执行逻辑分散在 HTTP controller 和 WebSocket 入口里，容易出现两个入口行为不一致。Tool Registry 把当前网页端 5 个 skill 和 OpenClaw 8 个 training tool 的元信息集中起来：工具名、类型、风险等级、是否需要确认、是否幂等、超时、服务端入口和结果摘要。

实际价值有三个：

1. 路由结果不直接落到散乱 `if/else`，而是通过 registry 找到可执行 skill。
2. 删除培训记录这种高风险动作可以在元数据层明确要求确认。
3. `/api/tools/registry` 能把系统已有工具暴露给治理页面和后续评测，方便检查“Agent 能调哪些工具、这些工具有多危险”。

这不是为了炫技加抽象，而是为了让 tool 使用可枚举、可审计、可测试。

### Q62：轨迹评测和意图评测有什么区别？

A：`eval:intent` 只验证“模型或规则把这句话判成哪个 skill”，例如“把之前培训记录删掉”必须识别成 `delete_training_records` 并要求确认。

`eval:agent-trajectory` 更进一步，验证“识别后有没有走正确执行轨迹”。比如：

- 删除记录第一次只能返回 `intent_confirm`，不能出现 `tool_execute:delete_training_records`。
- 确认删除必须先出现 `confirmation_verify:delete_training_records`，再出现 `tool_execute:delete_training_records`。
- “重新输入：给李小红发布培训”必须创建新草稿，不能发布旧草稿。
- 普通记忆指令只走记忆处理，不应误触发培训或删除工具。

这更接近成熟 Agent 项目的 trajectory eval：不是只看最终回答，而是检查中间工具选择、确认门禁和禁止误执行的约束。

### Q63：Agent Run 会不会泄露用户聊天内容或 API Key？

A：不会保存完整消息。Run 和 Trace 都只保存 `messagePreview`、`messageHash`、长度、step 摘要和耗时。`messagePreview` 会压缩长度，并对 `sk-...` 这类 API Key 形态和 `token/api_key/password/secret` 字段做脱敏。模型完整输出、完整用户消息、确认 token 和 API Key 不进入治理页面。

这个取舍是有意的：排障需要“足够判断发生了什么”的摘要，但不需要把所有对话内容变成新的敏感数据源。

### Q64：这次维护性重构主要解决了什么问题？

A：这次重构不是加新功能，而是清理前几轮快速迭代后出现的维护风险。主要做了三类事：

1. 后端运行层去重：HTTP controller 和 WebSocket stream 都改为复用 `src/agent` 下的确认校验、摘要和 run 收尾逻辑，避免两个入口各写一套 trace/finish/error 处理。
2. AI 层真拆分：`src/ai/core.mjs` 只保留兼容导出，实际代码按意图识别、RAG 上下文、答疑、讲义、软文、出题和文本工具拆开，避免所有 LLM/RAG 逻辑堆在一个大文件里。
3. 前端入口瘦身：老板端聊天把 session、纯渲染和记忆交互拆到 `public/src/chat/*`，Trace 页面把 Run/Trace/Tool 渲染拆到 `public/src/traces/*`。

同时把 `agent_runs` / `agent_steps` 的 SQLite 建表逻辑收敛到 `src/agent-runs/schema.mjs`，避免 `sqlite-store` 和 `agent-runs/store` 两边重复维护。

面试里可以这样说：

> 项目迭代到 Agent Run、任务中心、知识库版本这些能力后，我做了一轮维护性重构，把重复的运行治理逻辑、AI 大文件和前端大入口拆开。这个改动没有改变外部 API，但降低了以后继续加 skill、做 Trace 排障和维护 SQLite schema 的成本。

### Q65：为什么前端会看到 `**加粗**` 这类 Markdown 符号，怎么处理？

A：大模型默认很容易按 Markdown 组织答案，比如用 `**重点**`、有序列表和项目符号提升可读性。如果前端把模型输出当纯文本展示，用户就会直接看到这些语法符号。

项目里的处理方式不是要求模型完全不输出 Markdown，而是在前端普通聊天和软文正文增加轻量安全 Markdown 渲染：先对模型文本做 HTML 转义，再解析加粗、列表、标题、行内代码和代码块。这样既能提升显示效果，也避免把模型输出当成未受信任的 HTML 直接插入页面。

面试时可以这样表达：

> 我没有直接使用 `innerHTML` 渲染模型原文，而是先转义 HTML，再做有限 Markdown 解析。这样普通聊天可以保留大模型自然的 Markdown 排版，同时控制 XSS 风险和前端依赖复杂度。

### Q66：聊天记录为什么先做在前端 localStorage，而不是直接入库？

A：这个聊天记录主要是老板端界面的“会话回看”和“切换上下文”，不是业务事实数据。培训任务、考试成绩、知识库版本和记忆已经有各自的持久化模型；如果把界面聊天 HTML 也混进业务库，反而会增加清理、迁移和权限边界复杂度。

当前做法是：每个聊天会话绑定独立 `sessionId`，左侧列表保存在浏览器 `localStorage`，发送请求时继续把当前 `sessionId` 传给后端。前端自动清理 30 天前未更新的会话，避免本地记录无限增长。

这种方案的边界也很清楚：它适合单机老板端回看；如果未来要做多端同步、审计留痕或管理员统一检索，再把“会话记录”升级为 SQLite 表或服务端 API。
