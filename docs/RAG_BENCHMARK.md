# 钜洲培训 Agent RAG 规模基准

更新时间：2026-07-11

本报告记录 2026-07-10 至 2026-07-11 在专用 GPU 主机 `192.168.9.105` 上完成的 100 / 1000 / 5000 文件全生命周期基准。最终验收数据以 [rag-scale-20260710-final.json](artifacts/rag-scale-20260710-final.json)（version 2）为准；[rag-scale-20260710-remote.json](artifacts/rag-scale-20260710-remote.json) 是缓存修复前的 version 1 历史对照，不能作为当前容量或降级率的验收证据。

该主机是隔离的 Reranker/benchmark 环境，不是现有培训生产服务器。本轮没有连接、更新或重启培训生产服务器。

## 结论先行

- 按完整验收条件，当前单机方案的严格容量边界是 **100 文件 / 并发 20**。100 文件档的三路检索均为 0 错误、0 降级，最弱的 hybrid 仍有 Hit@3=99%，全生命周期内存、显存和磁盘也全部通过。
- 1000 文件档不能判定为容量通过：虽然 1200 次请求均成功且没有降级，但 hybrid Hit@3=92% 低于 95%，主机内存已用峰值 85.56% 也超过 80%。
- 5000 文件档同样不能判定为容量通过：hybrid Hit@3=91%，主机内存已用峰值 98.04%，并发生 5 次 reranker fallback；并发 20 时 hybrid 与 hybrid+reranker 的 p95 还分别达到 6135 ms 和 6492 ms。
- 若只观察**完成预热后的查询层**，BM25 在 5000 文件 / 并发 20 下为 0 错误、0 降级、Hit@3=100%、p95=22 ms；这证明热路径可承载该规模，但不推翻 5000 文件全生命周期内存未通过的事实。
- 同样只看预热查询层，5000 文件的 hybrid+reranker 在并发 5 下为 0 错误、0 降级、Hit@3=100%、p95=1668 ms，因此把 **并发 5** 作为“无降级 reranker”建议上限。并发 10 虽有 Hit@3=100%、p95=3271 ms，却已发生 1 次 fallback，不能宣称为纯 reranker 无降级容量。
- 未重排 hybrid 在 1000/5000 文件档的主要问题是质量而非请求错误；不能只凭时延达标就宣称大规模检索可用。

因此，对外应表述为“完整实测至 5000 文件，严格全生命周期容量为 100 文件 / 并发 20；预热查询层另有 5000 文件路线数据”，不能把“跑过 5000 文件”直接等同于“5000 文件整体容量通过”。

每档有 3 种模式 × 4 个并发级别，共 12 个网格、1200 次正式请求；三档合计 36 个网格、3600 次正式请求。所有 Hit@K 都基于确定性 ground truth；每个网格恰好 100 条查询，因此表中的命中数也等于百分比。

查询矩阵统计的是 warmup 之后的热路径，不包含进程冷启动、首次模型加载、首次 BM25 corpus/cache 构建和 embedding/index 构建时间。导入、embedding 和主机资源峰值则纳入全生命周期容量判断。

严格容量条件为：

- 请求错误为 0，且请求模式没有静默降级；
- 每一路检索 Hit@3≥95%；
- 单并发 p95≤2 秒，并发 10 p95≤5 秒；计算每档最大可用并发时，多并发网格使用 5 秒上限；
- 主机内存已用峰值低于 80%，显存已用峰值低于 95%；
- 剩余磁盘大于 20 GiB。

一个档位只有在质量、时延、降级和全生命周期资源都通过时，才计入整体容量。

## Reranker 降级证据

最终 3600 次正式请求全部成功，调用层错误数为 0；但 version 2 会同时记录“请求模式”和“实际模式”，因此能够识别无报错降级：

- 5000 文件 / 并发 10：1/100 次 `reranker_not_ready:fallback`；
- 5000 文件 / 并发 20：4/100 次 `reranker_not_ready:fallback`；
- 其他 34 个网格：0 次降级；
- 全部请求口径：5/3600，降级率 0.14%；
- 5000 文件档口径：5/1200，降级率 0.42%；
- 5000 文件 reranker 请求口径：5/400，fallback 率 1.25%。

全局实际模式计数为 BM25 1200、hybrid 1205、hybrid+reranker 1195。多出的 5 次 hybrid 正是 reranker 失败后的安全回退。它们没有造成请求错误或本组合的 Hit@K 下降，但违反“无降级”容量条件，必须保留为失败证据。

## 全生命周期容量与预热查询层的区别

| 观察口径 | 最大可诚实声称的结果 | 不应声称的内容 |
| --- | --- | --- |
| 全生命周期严格容量 | 100 文件 / 并发 20 | 不能称 1000 或 5000 文件整体容量通过 |
| 5000 文件 BM25 热查询 | c20，p95=22 ms，Hit@3=100%，0 降级 | 不代表 embedding/index 生命周期内存通过 |
| 5000 文件 hybrid 热查询 | c20 以下可运行，但 Hit@3 始终 91% | 不能因 0 错误就称质量达标 |
| 5000 文件 reranker 热查询 | 无降级建议 c5，p95=1668 ms，Hit@3=100% | c10 已有 1 次 fallback，不是纯 reranker 无降级上限 |

5000 文件 reranker 的 c10/c20 最终 Hit@1 仍为 100%，说明 fallback 本身没有让这组确定性型号查询失分；容量门槛仍将其判失败，是为了防止把“回退后恰好答对”掩饰成 reranker 服务稳定。

## BM25 缓存与旧 v1 对照

旧 version 1 运行暴露出 BM25 每次请求重复构建 corpus 统计的问题。最终实现按持久化 `chunksRevision` 和检索范围缓存 corpus，并按实际保留的文档唯一词项槽位计算 LRU 权重；构建完成后不再保留原始 token 数组。这既确保知识变更后缓存失效，也避免 5000 文件长文本因错误权重被反复逐出缓存。

| 对照项 | 旧 v1 | 最终 v2 |
| --- | ---: | ---: |
| 1000 文件 / BM25 / c20 p95 | 9925 ms | 8 ms |
| 1000 文件 / BM25 / c20 RPS | 2.02 | 2941.18 |
| 5000 文件 / BM25 / c20 p95 | 不作为最终对照结论 | 22 ms |
| 5000 文件 / BM25 / c20 RPS | 不作为最终对照结论 | 990.10 |

旧 v1 不记录完整的 requested/effective mode、reranker fallback 和降级聚合，且资源时间线与最终代码不同，因此只用于说明缓存热路径优化，不能拿它的较低资源峰值或单项路线数据替代 v2 容量结论。最终验收与所有对外数字均应引用 v2 artifact。

## 限制与适用范围

- 合成语料与 100 个确定性查询以明确型号标识为主，BM25 的 100% 不等于自然语言、多语言、跨知识库 hard negative 和无答案拒答也达到 100%；这些能力由 150 条分层 RAG 评测集单独约束。
- warmup=5 已排除查询冷启动影响，因此矩阵是稳定热路径数据，不是首次请求体验；生产观察仍需结合 TTFT、检索/rerank 延迟和实际请求分布。
- 主机级资源峰值可能包含长期 Reranker 服务和操作系统基线，但严格容量判断故意使用实际共享主机总量，避免低估真实部署风险。
- 5000 文件时 SQLite 为 154.84 MiB、JSON 向量索引为 258.12 MiB；继续扩容会增加全量加载、重建、备份和峰值内存成本。超过当前严格边界应优先评估 Qdrant/增量索引、分进程构建和资源隔离，而不是只提高并发。
- 本次证明的是当前代码、当前硬件、当前合成数据下的边界；真实业务容量上线前仍需使用生产等价语料复测，且不得用降低冻结测试门槛换取“通过”。
